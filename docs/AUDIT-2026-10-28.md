### WhatsApp-Web.js Ack Enum vs `updateMessageAckStatus` Comparison

#### 1. Installed `whatsapp-web.js` MessageAck Enum:
```javascript
// node_modules/whatsapp-web.js/src/util/Constants.js
MessageAck: {
  ACK_ERROR: -1,
  ACK_PENDING: 0,
  ACK_SERVER: 1,
  ACK_DEVICE: 2,
  ACK_READ: 3,
  ACK_PLAYED: 4
}
```

#### 2. Codebase `updateMessageAckStatus`:
```javascript
// src/services/database.js:1018-1056
async function updateMessageAckStatus(userId, waMessageId, ackStatus) {
    if (!waMessageId || typeof waMessageId !== 'string') return false;

    // Map WhatsApp ack integer → status string and ordinal rank
    const ACK_MAP = {
        [-1]: null,    // error — don't touch status
        0:    null,    // pending — don't touch status
        1: { status: 'sent',      rank: 1 },
        2: { status: 'delivered', rank: 2 },
        3: { status: 'read',      rank: 3 },
        4: { status: 'read',      rank: 3 }  // played (voice) = read
    };
    const mapped = ACK_MAP[ackStatus];
    if (!mapped) return false;

    // Only update if the new rank is strictly higher than the current rank.
    const res = await query(
        `UPDATE messages SET status = $1
         WHERE user_id = $2
           AND wa_message_id = $3
           AND direction = 'outgoing'
           AND CASE status
                 WHEN 'read'      THEN 3
                 WHEN 'delivered' THEN 2
                 WHEN 'sent'      THEN 1
                 ELSE 0
               END < $4`,
        [mapped.status, userId, waMessageId, mapped.rank]
    );
    return (res.rowCount || 0) > 0;
}
```
**Evaluation:** The mapping accurately reflects WhatsApp Web's protocol semantics. Un-delivered states (-1, 0) are discarded, voice played (4) is collapsed into read (3), and monotonic status upgrade is guaranteed by SQL rank ordering (`sent` < `delivered` < `read`), preventing status rollback on out-of-order packet delivery [VERIFIED-CODE].

## 4. WhatsApp Lifecycle Findings

### State Model & Transitions
The session object `s = sessions.get(userId)` in `src/services/whatsapp-client.js` transitions through the following states:

| State | Trigger | Flags & Fields | Timers Active | Truthfulness Check |
|---|---|---|---|---|
| `disconnected` | Manual Disconnect, Logout, or initial state | `isConnected=false`, `currentQR=null`, `userDisconnected=true` | None | Verified |
| `loading` | `initWhatsAppClient()` invoked | `isInitializing=true`, `startedAt=now` | `initWatchdog` (95s) | Enforced via queue |
| `qr_ready` | `client.on('qr')` fires | `currentQR=dataUrl`, `isInitializing=false` | `qrTimeout` (180s) | Replayed on late SSE |
| `authenticated` | `client.on('authenticated')` | `currentQR=null`, `isInitializing=false` | None | Watchdogs cleared |
| `loading_screen` | `client.on('loading_screen')` | Progress `percent` streamed to SSE | None | Watchdogs cleared |
| `connected` | `client.on('ready')` fires | `isConnected=true`, `crashCount=0` | `keepAlive` (15s), `watchdog` (90s) | Verified via `getState()` |
| `reconnecting` | Network drop or `getState() !== 'CONNECTED'` | `isConnected=false`, `crashCount++` | `restartTimer` (exp backoff 8s..300s) | Blocked if `userDisconnected` |

### States and Transitions Details
- **Where `Connected` is set:** `client.on('ready')` at line 759 sets `s.isConnected = true` and `s.isInitializing = false` [VERIFIED-CODE].
- **Live State Verification:** `getStatus(userId)` does not blindly trust `s.isConnected`. Every 10 seconds, it issues `client.getState()`. If `getState()` is not `CONNECTED` or times out, it tracks `s.staleConnectedSince`. If stale for >= 35s, it returns `state: 'disconnected'`, maintaining status truthfulness [VERIFIED-CODE].
- **Disconnect vs Logout Semantics:**
  - `POST /api/whatsapp/disconnect` with `{ wipeAuth: false }`: Calls `destroyClientForUser(id, { wipeAuth: false })`. Chrome process tree is killed, timers cleared, `wa_user_disconnected='true'` saved in DB. Saved auth credentials in `.wwebjs_auth/user_X` remain intact on disk.
  - `POST /api/whatsapp/disconnect` with `{ wipeAuth: true }` or `{ logout: true }`: Calls `s.client.logout()`, and deletes the `.wwebjs_auth/user_X` directory from disk.
  - Phone-initiated Logout (`client.on('disconnected', reason => reason === 'LOGOUT')`): Deletes `.wwebjs_auth/user_X` and broadcasts `logged_out` [VERIFIED-CODE].
- **Code Paths that Delete `.wwebjs_auth`:**
  1. `src/services/whatsapp-client.js:851-854`: `client.on('auth_failure')` deletes directory when WhatsApp rejects saved tokens.
  2. `src/services/whatsapp-client.js:876-879`: `client.on('disconnected')` with `reason === 'LOGOUT'`.
  3. `src/services/whatsapp-client.js:1140-1147`: `destroyClientForUser(userId, { wipeAuth: true })`.
- **Can Timers Restart After Manual Disconnect?** No. `scheduleRestart()` explicitly checks `if (s.destroyed || s.userDisconnected) return;`. `watchdogTimer` checks `if (s.destroyed || s.userDisconnected) return;`. `server.js` checks `wa_user_disconnected === 'true'` in the database on reboot before resuming sessions [VERIFIED-CODE].
- **Listener Registration & Leaks:** `attachHandlers()` is called once per `Client` instance in `initWhatsAppClient()`. Old client listeners are purged via `removeAllListeners()` in `safeDestroyClient()` before destruction. SSE response listeners (`req.on('close')`, `req.on('error')`, `res.on('error')`) cleanly remove clients via `removeSseClient()` [VERIFIED-CODE].
- **Late-Opened Modal QR Delivery:** If a user opens the modal after the QR is generated, `addSSEClient()` immediately sends `{ type: 'qr', data: s.currentQR }` from cache. If SSE fails, REST polling `/api/status` returns the QR. However, if the modal is opened >180s after generation, `s.qrTimeout` has fired and killed idle Chrome to free RAM, requiring the user to click "Connect" [VERIFIED-CODE].
